`beliefs.holdings.boundary.write` appends a holdings write intent to the observer corpus before the store write. When the store then refuses, no observation follows, and the holdings reducer (rules_v1 `_unsettled`) blocks that location as `unsettled`. It stays blocked until a later `re-check` intent at the same location is matched. Beliefs provides `recheck`, but no science command reaches it, so the block can only be cleared by writing around science.

Wanted: a science command (or an existing command's path) that re-checks a store location under the holdings permit and publishes the observed outcome (Absent here), settling the intent.

Instance: in the mm30 world, the working corpus holds chain entry 553be3ce71bdd8b48b17f534f335126be69d73a32950e1aab4ad64ecb17aef7d (event token 956c6da01fa221f94336d7dab1294e53) for location store:05b6c1225e710bb1559f36e8333f3f29:2061b3731c13ccf956499f10015d9312472edabafc0554b001bb35c0f8f44955/mask-key.json, left by invocation 6cf80d367660d05be56a00f686e7f23c (2026-10-30, mm-62e2da). Settling it is a world write and needs the user's authorization. The store is read-only-serviceable, but a re-check only reads it.

Established by the 2026-10-30 scope pass: science at 4bb82495bcadddff0b5e06e20aaa2a30bdf6b1c7 has no command reaching recheck. Beliefs at 405f24995bf0934fe4fc3cdd9fdb98be4dd2516a already supplies ScopedWriter.recheck in python/src/beliefs/session/writer.py, wrapping holdings/recheck.py with the invocation's ledgered seam, operation port and closing hold. Reuse that public session route rather than building a second recovery protocol around boundary.recheck. It requires holdings-observation via holdings and act-report via corpus-write, validates the bound store before effects, and reports inconclusive reads without publishing a false Absent observation. rules_v1/holdings.py::_unsettled requires the later matched re-check at the same location in the same corpus chain; a re-check in a different observer corpus does not repair this intent.

Remaining scope: design and expose a bounded, explicit science re-check command for a store location, then implement it after design and plan review. Prefer a distinct command over adding recovery side effects to dataset or verify (verify already means assessment replay). Settle the input spelling, configured-store binding, observer/write-root selection, standing observations, exact permit declaration, and report/refusal mapping. Start with one requested location; bulk recovery, automatic retries and store lifecycle changes are outside this task. The command reads the store but writes governed corpus and ledger evidence, so it must use the existing writer endpoint and never be labelled read-only. Return the kernel's actual Found, Absent or inconclusive result; the incident's expected Absent is historical evidence, not a value to assume.

Done: CLI/declaration/handler and documentation expose the reviewed command; a synthetic unmatched-write fixture becomes settled only after a matched re-check in its original observer corpus, with other locations unaffected. Cover Found and Absent, serviceable read-only store recovery, inconclusive/unserviceable reads retaining the block, invalid/foreign locators and insufficient permits refusing before effects, standing observations, and invocation report/ledger replay. Use the documented just test-one route for focused tests and the checkout's validated test policy for gates. Do not run a live repair as the acceptance test.

Where to look: [ref:framework] for permit and dispatcher invariants; tools/cli.toml and commands/dataset/ for command declarations; python/src/science/commands/dataset.py for locator and standing-observation construction; python/src/science/dispatch.py for report audit, close and refusal handling; python/tests/test_cmd_dataset.py, test_contracts.py, test_write_dispatch.py and test_dispatch_refusals.py for integration patterns. These tests were read, not run, during scoping.
