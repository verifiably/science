Why: `service_server`'s `server_close` (python/src/science/serve.py, `Server.server_close`) unlinks the socket and closes the listener first, then sets `_closing` and waits for the requests being answered to drain, then calls `on_close`. In that drain window `check_socket_path` (serve.py) sees no socket, so a second launcher on the same world passes the only cross-process guard, opens its own `WriterSession` on the same write root, and can begin a write while the first launcher's in-flight write is still finishing. The idea's premise that the kernel serializes writes per root holds only within one process: beliefs' `OperationLock` (beliefs python/src/beliefs/corpus.py, class docstring) is in-process by design and says "single-writer deployment across processes stays a stated obligation; no file lock here would make it otherwise", and the layer design names "a second launcher on the same source root" as that obligation's violation (beliefs docs/superpowers/specs/2026-08-29-user-and-autonomy-layer-design.md, the intent-position rule). So the overlap matters: the socket is the guard, and it must stand until the drain ends. Both launchers use `service_server` (mcp.py `serve` and serve.py `serve`), so one change covers both.

Done: `server_close` sets `_closing`, waits for `_answering == 0`, and only then stats and unlinks the socket (still while bound, the existing inode check) and closes the listener before `on_close`. During the drain a new connection is refused `permit-exceeded` (the existing refusal; a client retries after the launcher closes) and a second launcher refuses `socket already exists`. The accepted cost, written into the `server_close` comment: a SIGKILL during a hung drain leaves a stale socket, which `check_socket_path` already reports as the operator's to remove, and the coordination spec §5.3 amendment of 2026-10-26 already says a second stop signal kills a launcher a hung write holds open. Tests, RED first: in python/tests/test_launcher_stop.py beside `test_a_stop_signal_during_mcp_serves_eof_drain_lets_the_write_finish`, assert that while the drain is held the socket path still exists, a second launcher's `check_socket_path` refuses, and a fresh connection is refused `permit-exceeded`; keep `test_mcp_serve_accepts_cli_writes_on_the_socket_and_blocks_a_second_launcher` (python/tests/test_mcp_socket.py) green. Amend the coordination spec's 2026-10-26 §5.3 paragraph (docs/specs, "Closing waits for the socket requests being answered") to say the socket is removed after that wait, so a second launcher refuses until the session has closed.

Where to look: python/src/science/serve.py (`check_socket_path`, `service_server`, `Server.server_close`, commits fbeb32a and 0b0578d for the current order and its reason); python/src/science/mcp.py `serve` (the MCP launcher's close path, `server.server_close()`); python/tests/test_launcher_stop.py and python/tests/test_mcp_socket.py; the coordination spec §5.3 amendments.
