Why: ops-ab03a7 proved that pytest-testmon 2.2.0 (allowed by python/pyproject.toml:20 pytest-testmon>=2.2.0 and locked in python/uv.lock) increments TestmonXdistSync.await_nodes in pytest_testnodeready instead of pytest_configure_node, so faster xdist workers trigger sync_db_fs_tests while slower workers are still inside determine_stable() and abort test-fast with "Different tests were collected" whenever test nodeids are added or removed. Upstream commit af5ba5c26d43a4b07b8afecc96ed2bcfc8773e92 (https://github.com/tarpas/pytest-testmon/commit/af5ba5c26d43a4b07b8afecc96ed2bcfc8773e92) fixes the race and is published on PyPI in pytest-testmon 2.3.0b0 (preserving DATA_VERSION = 14 so existing .testmondata stays valid).

Change: in python/pyproject.toml:20, pin pytest-testmon==2.3.0b0 (with a comment citing upstream commit af5ba5c26d43a4b07b8afecc96ed2bcfc8773e92 and retiring the pre-release pin to >=2.3.0 once stable 2.3.0 ships), update python/uv.lock, keep fast_cmd in justfile:25 on "cd python && uv run pytest --testmon " + xdist (retiring the manual single-worker invocation workaround), and add a one-line comment above fast_cmd noting the >= 2.3.0b0 floor and one --testmon process per .testmondata at a time.

Done: python/uv.lock resolves pytest-testmon 2.3.0b0; just setup and a focused test-one run pass; repeated test-fast runs after adding a new test collect identical items across xdist workers without collection errors.
